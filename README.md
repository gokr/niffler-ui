# niffler-ui — the desktop SPA for a Niffler harness

A [Niffler](https://github.com/gokr/niffler) client: a Svelte SPA in a Wails v2
window. It is the *graphical* frontend; the harness itself is the thing that
runs agents, sessions and tools.

**The SPA is a NATS client, not a Wails client.** Every tool call, approval,
event and bit of state rides the bus; `frontend/src/nats.ts` is the only file
that talks to the outside world. Wails is a *hosting choice* — the same SPA
runs in a plain browser (`make dev`, bridge stubbed) with no SPA changes.

## Install

The supported way is through a Niffler checkout, which builds this package and
installs the launcher (bus resolution + boot-on-demand, like `niffler-tui`):

```bash
cd ~/git/niffler
make install WITH_UI=1        # or: make install-ui
niffler-ui                    # attaches to a live harness, or boots one
```

Requirements: Go 1.25+, Node 20+, the `wails` CLI
(`go install github.com/wailsapp/wails/v2/cmd/wails@latest`) and, on Linux,
webkit2gtk-4.1 + GTK3 development packages (`make install-ui-deps` in the
harness, or `apt install libgtk-3-dev libwebkit2gtk-4.1-dev`).

## Build it by hand

```bash
git clone https://github.com/gokr/niffler-ui
git clone https://github.com/gokr/niffler ../niffler   # sibling: the SDK lives here
cd niffler-ui && make build
./build/bin/niffler-ui
```

`go.mod` replaces `niffler.dev/sdk` with `../niffler/sdk/go` — the same
sibling-checkout convention `gokr/niffler-tui` uses. A harness that installs
this package from `var/plugins/` writes an untracked `go.work` instead, so the
SDK is taken from *the* harness that installed it; you can do the same by hand:

```bash
printf 'go 1.25.0\n\nuse .\n\nreplace niffler.dev/sdk => /path/to/niffler/sdk/go\n' > go.work
```

The app finds its harness in this order: `NIF_ROOT` → the root baked at build
time (`make build NIF_ROOT=/path/to/harness`, used for icon launches) → a walk
up from the executable looking for the marker `var/bin/niffler` → the
executable's own directory.

## Make targets

| target | what it does |
|---|---|
| `make build` | bindings → SPA → Wails binary in `build/bin/niffler-ui` |
| `make dev` | Vite dev server in a browser (bridge stubbed) |
| `make test` | frontend unit tests (`node --experimental-strip-types`, no deps) |
| `make typecheck` | `tsc --noEmit` + `svelte-check` |
| `make install` / `uninstall` | desktop integration: `~/.local/bin/niffler-ui` + `.desktop` entry + icons |
| `make clean` | drop `build/`, `frontend/dist/`, `frontend/wailsjs/` |

`frontend/wailsjs/**` is generated by Wails (`make bindings`) and gitignored;
`make bindings` seeds a placeholder `frontend/dist` first, because generating
the bindings compiles the Go package, which `//go:embed`s that directory.

## Relationship to the harness

- It registers on the bus as a component with **zero tools** and `client: true`
  — a UI, not a capability — which is how a core started by a UI knows to exit
  when the last client leaves.
- It reads and writes only documented surfaces: `docs/WIRE.md` (envelopes,
  `ev.session.<id>.*`, `svc.core.call`) and the store's `conversation` /
  `message` kinds. Nothing else is API.
- The conversation UI, slash commands and approvals are the SPA's business; the
  harness keeps a thin launcher (`scripts/niffler-ui.in`) because *starting the
  harness* is the harness's job.
